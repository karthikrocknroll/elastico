Improvement — E-21 (Boundary, actual-age play-up cap)
Before
E-21 (the boundary case) initially returned STATUS: OK, recommending an ineligible candidate for the Hawks' U10 request. The real boundary candidate, Mason Reilly, actually fails the play-up cap (actual age 6 vs the destination's nominal age 10, a 4-year gap) but the model missed this - on one run it even justified excluding a different candidate by inventing a rule that does not exist ("shared Age Coordinator" conflict) instead of citing a real one.
Change
Two fixes. Context wiring: each candidate's own team's game time (SourceTeamGame) was missing from the data sent to the agent, so it was guessing at scheduling conflicts instead of checking real data - added it. System prompt: reordered the required output so the agent writes its full analysis (WHY) before its conclusion (STATUS/REASON), and added an explicit instruction forbidding invented eligibility rules not present in the policy files.
After
E-21 now consistently returns STATUS: REFUSED-ESCALATE, correctly citing "actual age 6 vs destination nominal age 10, difference 4, exceeds the 2-year cap" (eligibility_rules.md §1b) - holding across repeated re-runs.
Known Limitations
  • Handles only the Match Making + Approve/Reject step of the workflow. The weekly reminder, Pulse Check request-creation, auto-cancellation, the 8-hour Super Admin escalation, and week-end rollover are not built.
  • English only, one Borrow request evaluated at a time. Run All processes the queue sequentially, not in parallel.
  • Human decisions (Approve / Reject / Override) are logged, not enforced. They don't mutate the underlying Team/Player/Borrow/Loan data, so a rejected or approved candidate isn't actually removed from the pool - re-running the same case can still recommend the same candidate again.
  • Needs data in the exact embedded schema (Team, Player, Game, Borrow, Loan records as JS objects inside index.html). There's no file upload, CSV import, or live database - the dataset is fixed and synthetic, sized to exercise 5 known eval cases plus a few filler cases, not a real club's full season.
  • Single local API key stored in one browser's localStorage. No accounts, no multi-user access, no server - nothing is shared or synced between people running the file.
  • The Selection Order logic (eligibility_rules.md §8) is written to handle the At Risk urgency tier correctly in principle - it should never let a time-pressured request jump ahead of one whose team hasn't met Minimum - but this is unverified by any eval case, since At Risk's own trigger (the day-before-game-day timer) isn't built in this prototype. Noted as an accepted, out-of-scope gap.
Gotchas (found and resolved after Section C was marked complete)
  • Resolved - Selection Order (eligibility_rules.md §8) let lower-urgency Borrow requests act as competitors. Found via E-08: three genuinely valid candidates were all wrongly excluded because the agent checked them against B-E01, B-F01, and B-F04 - all Medium or Low urgency, none actually eligible to compete under the "same tier or higher" rule. It also let one competing request "claim" more than one candidate at a time, when a request only ever needs one. Fixed by making the urgency-tier filter and the one-candidate-per-competitor rule explicit in the system prompt. Re-run confirmed: E-08 now correctly returns OK with Liam Cooper. This surfaced through continued use after the formal eval pass, not through the graded eval suite itself - a clean scoreboard doesn't guarantee no regressions. (See the two related Selection Order findings below, surfaced later via E-21/E-27 and E-29.)
  • Resolved - A second, related issue surfaced through E-27 after the fix above, revealing two separate problems stacked on top of each other. First, a genuine business-rule error, not an agent bug: eligibility_rules.md §3 (and the Discovery/Design PRDs it was built from) wrongly stated that a Girls-only-team player could never be eligible for a Mixed-team Borrow request. The real rule is that a Female player is eligible for either team type - only male players are restricted, and only from Girls-only requests. Corrected across the PRDs, the Business Logic document, eligibility_rules.md §3, and the system prompt. Second, fixing that revealed Ruby Anderson (a Girls-only-team Female) is legitimately eligible for both E-27's own request and a separate High-tier request (B-E21) requested 30 minutes earlier - and on the first re-run, the agent incorrectly awarded her to BOTH in two separate runs, because it dismissed B-E21 as "not competing" purely because the destination Types differ, without re-testing her actual eligibility. Fixed by explicitly forbidding that shortcut in the system prompt. Re-run confirmed: E-27 now correctly returns REFUSED-ESCALATE (Ruby legitimately lost to the earlier B-E21), and E-21 now correctly returns OK - Ruby Anderson. This reclassified E-21 - it is no longer the "must refuse" boundary case, so E-29 was added to preserve that demonstration. E-21 and E-27 are now presented as one merged eval case (E-21, covering both B-E21 and B-E27) in the formal five, the same way E-28 already pairs B601 and B602 - the template calls for five cases (1 happy path, 3 edges, 1 boundary), and this keeps every individual demonstration one click away without exceeding that count.
  • Resolved - While verifying the new E-29 boundary case (added to replace E-21 as the "must refuse" demonstration), the agent's first run incorrectly recommended Sophie Bennett despite her own team's game being at the exact same date/time as the destination's game, reasoning that a different LocationName meant "no conflict" - backwards from eligibility_rules.md §4, which is a date/time-only check; location is irrelevant to whether a player can be in two places at once. Fixed by explicitly stating in the system prompt that a matching GameAt is always a conflict regardless of LocationName. Re-run confirmed: E-29 now correctly returns REFUSED-ESCALATE, with every candidate ruled out for a different, independently-verified reason. Found only because a boundary case was deliberately re-verified rather than assumed to still work after an unrelated fix.
